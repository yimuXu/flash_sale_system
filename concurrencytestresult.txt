FLASH SALE SYSTEM - CONCURRENCY & LOAD TEST RESULTS
====================================================

Environment
-----------
- App:        Spring Boot 4.1.1, Java 21, embedded Tomcat (default 200 threads), HikariCP (default 10 connections)
- Database:   PostgreSQL 18 (local)
- Cache:      Redis 7 (Docker)
- Queue:      RabbitMQ 4 (Docker), phase 3 only: 5 consumer threads, prefetch 10, 3 retries then dead-letter queue
- Load tool:  k6 (Docker, grafana/k6), scenario "per-vu-iterations": 1000 VUs x 1 request, all fired at once
- Endpoint:   POST /seckill/{productId}/{userId}, each VU uses a distinct userId
- Machine:    Windows 11, single host (app, DB, Redis and k6 on the same machine)

  How each row was measured
  - Phase 1 and 2 rows are SINGLE runs. Phase 3 rows are the MEDIAN of 3 warm runs.
    The phases are therefore not yet measured the same way (see TODO).
  - In phase 3 "Success" means HTTP 202: the request won the stock in Redis and its order
    was queued. The order row is written to the database afterwards by the consumer.
  - "Throughput" is 1000 requests / wall time of the single burst. It shows how fast one
    burst is cleared, not the sustained request rate the server can hold.
  - One extra phase 3 run (stock 100) was discarded: 155 requests got "connection refused"
    before reaching the app. Runs with network errors are not counted. Cause not confirmed.

  * Run marked 2* reported negative rates (e.g. -38819 req/s): the Docker VM clock
    jumped during the test, so throughput is invalid and latency is unreliable.
    Needs to be re-run before being quoted.

  "Failed (non-2xx)" is k6's http_req_failed. For a flash sale this mostly counts
  expected business rejections (HTTP 409 sold out / conflict), not server errors.

3. Findings
-----------
Phase 1 -> Phase 2
- Lock conflicts eliminated: 822 -> 0. The only rejection reason left is "sold out".
- No under-selling: with stock 1000 and 1000 users, all 1000 purchases succeeded (0% failure).
- p95 latency reduced by ~50% (1.85 s -> 925 ms); throughput up ~78% (437 -> 777 req/s).

Remaining bottleneck
- Requests that only touch Redis (sold out) still had a median of ~470 ms, while the
  fastest request took 33 ms. Time is spent queueing, not processing.
- Winning requests still write to the database synchronously (UPDATE on the same hot row
  + INSERT) through only 10 DB connections. They hold Tomcat threads while waiting,
  so Redis-only requests queue behind them.
- Next step (Phase 3): asynchronous order creation via a message queue - return
  immediately after the Redis check and let a consumer write orders to the DB.

Phase 2 -> Phase 3 (PROVISIONAL - phase 2 baseline must be re-measured first)
- Stock 1000 (every request wins): p95 977 ms -> 299 ms, average 613 ms -> 224 ms.
  All 1000 requests return after the Redis check and one publish; the database is
  written by 5 consumers in the background instead of by 1000 request threads.
- Stock 100: NOT established. The two phase 2 runs disagree by 5x (925 ms vs 169 ms p95),
  and the faster one is in the same range as phase 3 (177 ms). With only 100 orders to
  write, asynchronous order creation may bring little latency gain.
- In phase 3 a winning request (Redis + publish) is still slower than a sold-out request
  (Redis only): stock 100 median over all requests was 29-59 ms, winners averaged 126 ms.
