FLASH SALE SYSTEM - CONCURRENCY & LOAD TEST RESULTS
====================================================

Four versions of the same flash-sale endpoint were measured:
  Phase 1  Optimistic locking in the database (JPA @Version)
  Phase 2  Stock pre-deduction in Redis with a Lua script, order written to the database synchronously
  Phase 3  Same Redis check, order written asynchronously through RabbitMQ
  Phase 4  Phase 3 plus a Sentinel rate limit on the endpoint

Sections 1-3 compare phases 1-3 with a single burst of 1000 requests.
Section 4 measures phases 2, 3 and 4 under sustained load.


Environment
-----------
- App:        Spring Boot 4.1.1, Java 21, embedded Tomcat (default 200 threads), HikariCP (default 10 connections)
- Database:   PostgreSQL 18 (local)
- Cache:      Redis 7 (Docker)
- Queue:      RabbitMQ 4 (Docker), phase 3 only: 5 consumer threads, prefetch 10, 3 retries then dead-letter queue
- Load tool:  k6 (Docker, grafana/k6), scenario "per-vu-iterations": 1000 VUs x 1 request, all fired at once
- Endpoint:   POST /seckill/{productId}/{userId}, each VU uses a distinct userId
- Machine:    Windows 11, single host (app, DB, Redis, RabbitMQ and k6 on the same machine)

Method
------
- Each phase runs from its own git tag (phase-1, phase-2, phase-3) against the same database and scripts.
- After starting the app, the first burst is a warm-up and is discarded.
- Each figure below is the MEDIAN of 3 measured runs. The database and Redis are reset before every run.
- A run is discarded and repeated if any request fails at the network level ("connection refused").
- "Burst rate" is 1000 requests / wall time of the burst. It shows how fast one burst is cleared,
  not the sustained request rate the server can hold.
- Tomcat accept queue: every data set in the tables was measured with
  server.tomcat.accept-count=1000 (the default is 100). See finding 5 for why it was raised.
  Earlier sets measured with the default are kept in the appendix. Sets measured with
  different settings are not comparable on latency.
- Two k6 timings are reported. "http_req_duration" runs from sending the request to the end
  of the response. "iteration_duration" is the whole request as the client sees it and also
  includes opening the connection, which here goes through Docker's network layer.

3. Findings
-----------

1) Optimistic locking under-sells badly.
   With stock for all 1000 users, phase 1 sold only 114 items (11%). The other 886 requests
   were rejected by version conflicts although stock was available. Phases 2 and 3 sold all 1000.
   With stock 100, phase 1 did sell out, but 775 of its 900 rejections (86%) were lock conflicts
   rather than "sold out".

2) Moving the stock check to Redis removes the lock conflicts.
   Stock 100, phase 1 -> phases 2 and 3: lock conflicts 775 -> 0. The only rejection reason
   left is "sold out".

3) Later phases have a lower http_req_duration, but the whole burst is not faster.
   All measured with the same accept queue (1000):
     stock 100,  phase 1 -> 2 -> 3    http_req_duration  avg 249 -> 97 -> 75 ms,    p95 385 -> 240 -> 216 ms
                                      whole request      avg 357 -> 413 -> 381 ms,  p95 532 -> 596 -> 627 ms
                                      burst rate         1297 -> 1181 -> 1195 req/s
     stock 1000, phase 2 -> 3         http_req_duration  avg 395 -> 308 ms,  p95 655 -> 483 ms
                                      whole request      avg 513 -> 548 ms,  p95 782 -> 843 ms
                                      burst rate         920 -> 825 req/s
   At stock 100, phases 2 and 3 do not differ beyond the spread between runs.
   The time outside http_req_duration ranged from about 110 to 310 ms between data sets and
   was largest for phase 3. The reason is not known: the k6 summary used here does not break
   it down (see TODO).
   Phase 3 also varies more between runs at stock 1000 (average 228-530 ms over 4 runs,
   phase 2 385-445 ms over 3).
   Earlier sets measured with the default accept queue looked faster for phases 2 and 3
   (for example phase 3, stock 1000 at 299 ms p95). Comparing them with accept-1000 sets mixed
   two settings, and those comparisons are withdrawn.
   What phase 3 changes is where the work happens: orders are written by 5 consumers at a
   bounded rate instead of by the request threads, failed writes are retried and dead-lettered,
   and a request no longer waits for the database. A single burst that the database can absorb
   in under a second does not measure that.

4) Phase 1 looks fast at stock 1000 only because it does a fraction of the work.
   Its p95 of 287 ms covers 114 completed orders and 886 early rejections. Phase 2 completes
   all 1000 orders in the request. The latency of phase 1 at stock 1000 is not comparable.

5) The default Tomcat accept queue is too small for a 1000-connection burst.
   Some runs lost requests to "connection refused" before they reached the application.
   Phase 2, stock 1000: 6 of 7 runs were affected with the default queue of 100; after setting
   server.tomcat.accept-count=1000, 0 of 3 runs were affected. Phase 1 also ran with 1000 and
   one of its 7 runs still lost 67 requests, so a larger queue reduces the problem but does
   not remove it.
   A bigger queue only lets more connections wait. The planned fix is rate limiting at the
   entry point (phase 4), so excess traffic is rejected deliberately instead of refused.

6) The first burst after startup is several times slower and must not be measured.
   Measured once directly (phase 2, stock 100, default queue): 749 ms p95 on the first burst,
   168 ms once warm (4.5x).
   Earlier single-run figures in this file (1.85 s, 925 ms, 977 ms p95) were taken without
   the warm-up procedure and are superseded by the tables above.

7) In phase 3 a winning request is still slower than a sold-out one.
   Stock 100: all requests averaged 75 ms, winners 163 ms. The extra time is the status write
   and the publish to RabbitMQ. Not yet investigated.


4. Sustained load and rate limiting (phases 2, 3 and 4)
-------------------------------------------------------
Method: k6 "constant-arrival-rate", a fixed number of requests per second for 30 s
(loadtest/steady.js). Every request uses a different user and the stock is larger than the
number of requests, so every admitted request wins: Redis check, status write, publish to
RabbitMQ. This is the most expensive path. One warm-up run, then ONE run per rate.
accept-count 1000. Latency is k6 http_req_duration.

4a. Capacity without a rate limit (phase 3)

  Target rate | Served     | Median  | p95     | p99     | Requests k6 could not send
  ------------+------------+---------+---------+---------+---------------------------
     500 /s   |  502 /s    | 2.7 ms  | 3.8 ms  | 6.6 ms  |       0
    1000 /s   | 1032 /s    | 2.9 ms  | 5.1 ms  | 14 ms   |       0
    2000 /s   | 2038 /s    | 5.3 ms  | 436 ms  | 493 ms  |      20
    3000 /s   | 2196 /s    | 994 ms  | 3.41 s  | 3.55 s  |   19455

  Latency is flat up to 1000 requests/s. At 2000/s the median is still 5 ms but the system
  stalls intermittently (p95 436 ms). At 3000/s it is overloaded: it serves about 2200/s,
  responses take seconds, and the load generator runs out of free virtual users.
  The rate limit was set to 1000 requests/s, the highest rate measured with flat latency.

4b. With a Sentinel limit of 1000 requests/s (phase 4)

  Target rate | Admitted (202)    | Rejected (429) | Admitted: median / p95 / p99 | Rejected: median / p95 | Could not send
  ------------+-------------------+----------------+------------------------------+------------------------+---------------
     500 /s   | 15001 (518 /s)    |       0        | 2.6 ms / 3.8 ms / 7.0 ms     |          -             |       0
    2000 /s   | 29133 (1004 /s)   |    30868       | 4.0 ms / 27 ms / 319 ms      | 1.5 ms / 7.1 ms        |       0
    3000 /s   | 29295 (1008 /s)   |    60489       | 8.5 ms / 178 ms / 361 ms     | 1.7 ms / 24 ms         |     217

  Same target rate, without and with the limit (p95 of admitted requests):
    2000 /s   436 ms -> 27 ms
    3000 /s   3.41 s -> 178 ms, and every request gets an answer (3088 /s served instead of
              2196 /s; requests that could not be sent 19455 -> 217)

  Findings
  - The limiter admits almost exactly the configured rate (1004 and 1008 requests/s).
  - Below the limit it changes nothing (500/s: p95 3.8 ms with and without).
  - Above the limit, admitted requests are 16-19x faster at p95 than without a limit, and
    rejected requests are answered in about 1.5 ms.
  - The tail is not flat: p99 stays at 320-360 ms for admitted and rejected requests alike,
    so the intermittent stalls seen at 2000/s without a limit are still there. Their cause
    is not known.
  - After the 3000/s run: 29295 orders, database stock = Redis stock = 66705, dead-letter
    queue empty.

4c. What the queue does under sustained load
  In the unlimited 3000/s run the endpoint accepted 70546 orders in about 32 s (2196 /s). The
  consumers wrote them to the database over 74 s (first and last order timestamps), about
  950 orders/s. The difference waited in RabbitMQ and was written after the load stopped;
  all 70546 orders were written and the dead-letter queue stayed empty.
  With the limit at 1000/s the 29295 admitted orders were written over 36 s, so the backlog
  stays small.

4d. Phase 2 under the same load (order written in the request, no queue, no rate limit)

  Target rate | Phase 2: served / median / p95 / not sent | Phase 3: served / median / p95 / not sent
  ------------+-------------------------------------------+------------------------------------------
     500 /s   |  499 /s / 4.3 ms / 5.8 ms / 0             |  502 /s / 2.7 ms / 3.8 ms / 0
    1000 /s   |  983 /s / 247 ms / 417 ms / 0             | 1032 /s / 2.9 ms / 5.1 ms / 0
    2000 /s   |  973 /s / 3.97 s / 4.07 s / 26719         | 2038 /s / 5.3 ms / 436 ms / 20

  - Phase 2 cannot serve more than about 975 requests/s. Each request writes its order before
    it answers, so the endpoint is only as fast as the database. This matches the consumer
    write rate measured in 4c (about 950 orders/s).
  - Phase 3 accepts 2000 requests/s with a 5 ms median and about 2200/s at most, roughly twice
    the intake of phase 2. At 1000/s its p95 is 5 ms against 417 ms.
  - The queue does not make the database faster. Orders are still written at about 950/s:
    phase 3 answers the user first and writes later. Intake above that rate can only be
    sustained for as long as the backlog is allowed to grow.
  - After the phase 2 run at 2000/s: 33283 orders, database stock = Redis stock = 30717.


5. Limitations
--------------
- Everything, including the load generator, runs on one machine, so the components compete
  for CPU and the absolute numbers are specific to this machine.
- Three runs per data point in sections 1-3. Run-to-run spread is visible in the appendix.
- Section 4 figures come from a single 30-second run per rate. The phase 2 runs were made
  four days after the phase 3 and 4 runs.
- A single 1000-request burst measures burst latency, not sustained throughput.
- Phases 2 and 3 at stock 100 were each measured twice, first with the default accept queue
  and later with 1000. Both were slower the second time by a similar amount (burst rate
  1786 -> 1181 and 1798 -> 1195 req/s). The larger queue is the likely cause, but it was not
  isolated from the state of the machine at the time.
